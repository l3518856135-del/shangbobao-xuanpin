## 一、作品概述

「上播前·选品体检」是一款面向助农直播基地选品员、运营人员的**选品合规决策工具**。它把"这个品能不能上播、缺什么、怎么改"这三件事，做成一条六步可复跑的流水线：**分流 → 资料录入 → 证据核验 → 规则判定 → 人工审核 → 档案/整改单**。

产品的核心不是"查违禁词"，而是**分级判定 + 人工签字留痕 + 可溯源导出**的决策工作流。判定结果分为四种状态：

| 状态 | 含义 | 处置 |
|---|---|---|
| 红·禁播 | 存在硬性违法/违规事实 | 禁播，不出整改单 |
| 黄·整改 | 整改后可播：待核验 / 缺项 / 表述需修改 | 出整改单，限期 7 日 |
| 绿·可播 | 类型正确、资质齐全有效、宣称合规 | 出具通过档案 |
| 灰·信息不足 | 无法判定，**不误判为违规** | 出待补充材料清单 |

**技术形态**：纯前端单页应用（HTML + CSS + JavaScript），**零后端、零构建、零安装**，双击 `index.html` 即可运行；所有数据留在本机浏览器，不上传云端。

## 二、技术架构

### 2.1 总体架构

| 层 | 组成 | 运行位置 |
|---|---|---|
| 界面层 | `index.html`（六步流程与各功能区）、`styles/main.css`（含打印样式） | 浏览器本地 |
| 逻辑层 | `js/app.js`（流程控制 / 渲染 / 存储）、`js/engine.js`（规则判定）、`js/validate.js`（字段校验） | 浏览器本地 |
| 数据层 | `data/rules.json`（权威源）+ `js/rules-data.js`（运行时镜像）；`localStorage`（草稿 / 档案 / 误报 / 密钥） | 本机 |
| 外部服务 | 智谱 `open.bigmodel.cn`（仅 OCR 可选，用户主动配置密钥时才访问） | 云端（可选） |

| 文件 | 职责 | 规模 |
|---|---|---|
| `index.html` | 界面结构：分流卡片、录入表单、核验/判定/审核/档案/整改单/规则库/隐私页 | 433 行 |
| `styles/main.css` | 视觉样式、四态配色、`@media print` 双通道打印 | 1198 行 |
| `js/rules-data.js` | 规则库运行时数据（21 条），供 `file://` 双击运行 | 74 行 |
| `data/rules.json` | 规则库权威源（先改 JSON，再同步 JS） | 21 条 |
| `js/validate.js` | GB 32100 校验位实算、SC 结构校验、日期/临期判断 | 104 行 |
| `js/engine.js` | 词表命中 + 字段一致性 + 报告实体比对，聚合四态 | 208 行 |
| `js/app.js` | 状态机、动态表单、核验、判定渲染、审核、档案、整改单、OCR、演示模式 | 1282 行 |

**为什么不用后端**：助农直播基地普遍网络不稳定、IT 基础薄弱，且选品资料含企业证照与信用代码，属于敏感经营信息。纯前端方案让工具可以离线运行、零部署成本、资料不出本机，这与"选品员在工位上随手就查"的使用场景一致。

**规则库为什么有两份**：浏览器在 `file://` 协议下会拦截 `fetch()` 读取本地 JSON（同源策略），因此把同一份规则以 `window.RULE_BASE` 形式内联到 `js/rules-data.js`，保证双击即用；`data/rules.json` 作为人工编审的权威源，修改后同步到 JS。

### 2.2 六步数据流

| 步骤 | 输入 | 处理 | 输出 |
|---|---|---|---|
| 1 分流 | 产品类型 / 销售主体 / 带货平台 | 映射到规则线（食用农产品 / 预包装 / 保健食品 / 地理标志） | 适用规则线摘要，未选类型则禁止进入下一步 |
| 2 资料录入 | 产品信息、宣称文案、资质字段 | 按类型动态渲染资质字段；草稿实时存 localStorage | 结构化表单数据 |
| 3 证据核验 | 表单字段 | 调用 `validate.js` 做可算的字段校验 | 通过 / 需修正 / 人工核对（三类） |
| 4 规则判定 | 表单数据 | 调用 `engine.js`，词表命中 + 一致性交叉 + 报告比对 | 四态等级 + 命中明细 + 灰级待补充清单 |
| 5 人工审核 | 判定条目 | 逐条裁决（确认违规 / 标记误报 / 忽略）+ 结论 + 签字 + 日期 | 写入本地档案；误报沉淀到误报库 |
| 6 档案导出 | 已签字档案 | 渲染五小节档案；黄态另可出整改单 | 可打印/PDF 档案、整改单 |

### 2.3 本地数据与隐私

| localStorage 键 | 内容 | 清除方式 |
|---|---|---|
| `shangbobao_xuanpin_draft_v1` | 录入草稿 | 隐私页「清除本地全部数据」 |
| `shangbobao_xuanpin_review_v1` | 已签字审核档案 | 同上 |
| `shangbobao_xuanpin_misreport_v1` | 误报沉淀记录 | 同上 |

## 三、核心判定机制

### 3.1 四态聚合规则

判定引擎为每条命中规则给出等级，最终结果取**最高严重度**：

```
RED(4) > YELLOW(3) > GRAY(2) > GREEN(1)
```

**灰态的触发条件**（关键防误杀设计）：

> 若规则层未命中任何硬性违规（结果为绿），但该产品线的关键字段存在缺失，则**升级为灰·信息不足**，并列出待补充清单；不判违规，也不判可播。

各产品线必填字段（缺失即灰）如下：

| 产品线 | 必填（缺失转灰） |
|---|---|
| 通用 | 产品名称、申报品类 |
| 预包装食品 | 统一社会信用代码、标签完整性、营养成分表、生产日期 |
| 保健食品 | 蓝帽子标识、法定警示语 |
| 食用农产品 | 承诺达标合格证 |
| 地理标志 | 专用标志授权证明、产区一致性 |

> 注：SC 号、保健食品注册号为空已分别由 R-YB-001、R-BJ-002 判红，不重复计入灰级清单，避免"同一问题既红又灰"。

### 3.2 双轨设计：硬规则与语义提示分离

| 轨道 | 特征 | 当前状态 |
|---|---|---|
| **RULE（硬规则）** | 词表命中 / 字段一致性 / 实体比对，结果 **100% 可复核** | 已落地 15 条 |
| **AI-SEMANTIC（语义）** | 由大模型做语义判断，**只提示、不判定**，须人工终审 | 预留接口，当前不产出判定 |

这条分界是产品的可信度基础：**能用规则算清的一律用规则算**，不把不可复核的判断包装成"判定结论"。

### 3.3 三条判定通路

1. **词表命中**（宣称文案，**包装与口播分开采集**）
   疾病/医疗用语词表、保健功能词表、绝对化用语词表、承诺性效果词表、虚构权威背书词表，命中即出对应规则，并在判定明细中标明来源（包装 / 口播）。

2. **字段一致性交叉**（各产品线）
   例：预包装无 SC → 生产/自销主体判红、**经销主体降黄**（《食品安全法》第三十五条：仅销售预包装食品不需许可，只需备案）；SC 非 14 位数字 → 黄；标签缺项 → 黄；营养表缺失 → 黄；过期 → 红（由黄升红）；临期/未来日期 → 黄；保健食品无蓝帽/无注册号 → 红；食用农产品无承诺达标合格证 → 黄、**畜禽类未提供检疫合格证明 → 红**（《食品安全法》第三十四条第（八）项：未按规定检疫的肉类属禁止生产经营食品）；地标无授权 → 红、产区不一致 → 黄。

3. **实体比对**（R-COM-006 检测报告）
   将报告上的产品名/规格/批号与申报产品比对：**名或规格不符、检验结论不合格 → 红**；**批号不符、缺 CMA/CNAS 标识、报告过期 → 黄**（多命中项合并为一张卡，取最高等级）。

### 3.4 防误杀设计（本产品的关键设计取舍）

| 风险 | 设计对策 |
|---|---|
| 把初级农产品当预包装要 SC | 分流先行；食用农产品线不采集 SC，核验项显式输出"无需 SC 证，跳过该项" |
| 字段为空被当作违规 | 空值不参与判定；缺信息走灰级清单 |
| 绿态但资料不全被判可播 | 绿 + 关键字段缺失 → 灰·信息不足 |
| 报告名与产品名有括号/简称差异被误判 | 归一化：去空白、去括号补充说明、小写；**归一化后完全相等才视为同一**（2026-10-25 起不再用“互相包含”，防止“苹果汁”包含“苹果”绕过） |
| 报告没填就判造假 | 报告字段任一为空即跳过比对 |

### 3.5 规则库落地覆盖（如实说明）

规则库共 **21 条**（v0.2 修订稿）：通用宣称（COM）6 条、预包装（YB）6 条、保健食品（BJ）4 条、食用农产品（NC）3 条、地理标志（DL）2 条；等级分布为红 9 / 黄 11 / 灰 1。

**当前引擎已接入 18 条**，另有 3 条仅入库、暂未接入判定，原因如下：

| 规则 | 名称 | 未接入原因 |
|---|---|---|
| R-YB-003 | SC 类别码与申报品类不符 | 需录入 32 类食品生产许可分类目录对照表（当前占位） |
| R-BJ-003 | 宣传超出注册批准功能 | 需录入保健食品 27 项获批功能范围（当前占位） |
| R-NC-002 | 食用农产品误标 SC | 属提示性防误杀条目，已由分流与核验文案覆盖 |

> 规则库查看页对全部 21 条公开展示，**并对未接入的 3 条显式标注"未启用"**，页面顶部注明"已启用 18 条 · 未启用 3 条"，不做"21 条全生效"的暗示。
>
> 其中 **R-YB-003（SC 类别码 × 申报品类）本期不做自动判定**：32 类分类目录对照表工作量大，统一转人工核验；答辩口径与此一致，不宣称已实现类别码自动识别。

## 四、字段校验算法

### 4.1 统一社会信用代码（GB 32100-2015）

实现为 `js/validate.js` 的 `validateUSCC`，第 18 位校验位**本地实算**：

- 字符集（31 位，剔除易混字符 I/O/S/V/Z）：`0123456789ABCDEFGHJKLMNPQRTUWXY`
- 权重（前 17 位）：`W[i] = 3^i mod 31`，即
  `[1, 3, 9, 27, 19, 26, 16, 17, 20, 29, 25, 13, 8, 24, 10, 30, 28]`
- 计算：`S = Σ Cᵢ × Wᵢ`，`C = charset[(31 − S mod 31) mod 31]`
- 判定：第 18 位与 C 相同 → 通过；不同 → 报出"应为 X，当前为 Y"

**边界**：只校验结构合法性，**不联网验真、不查企业是否存在**。校验位通过只说明"这个号码写法合法"，不等于"该企业真实存在且持有该证"。

示例：`91370100MA3D8C2K54` 的校验位为 `4`，本地可复算通过（该号码为演示虚构值）。

### 4.2 SC 食品生产许可证编号

- 结构：`SC` + 14 位数字（共 16 字符）
- 判定：数字部分长度或字符不符 → 黄（R-YB-002）
- **边界**：第 14 位校验码算法未公开，**不校验末位正确性、不查库**

### 4.3 生产日期 / 保质期

| 情形 | 结果 |
|---|---|
| 日期格式非法 / 晚于今天 | 提示日期异常（黄） |
| 已过保质期 | 红（R-YB-006 由黄升红） |
| 剩余天数 < 保质期 1/3 | 临期（黄），建议标注 |
| 保质期无法解析 | 只校验日期有效性，不做临期判断 |

保质期解析规则：`天` 按 1 天、`个月/月` 按 30 天、`年` 按 365 天折算。

## 五、API 调用逻辑

### 5.1 唯一的外部 API：智谱多模态 OCR

本产品**只调用一个外部 API**，且为可选功能（证照/标签图片识别）。调用链路：

1. 用户在录入页选择一张包装/标签图片
2. `FileReader` 在本地把图片转成 dataURL（图片本身不经由任何中转服务器）
3. 检查本地是否已配置密钥：**未配置 → 提示"已切换手录"，流程继续，不报错**
4. 已配置 → `POST https://open.bigmodel.cn/api/paas/v4/chat/completions`
5. 解析返回 JSON（剥离 markdown 围栏后 `JSON.parse`）
6. 按 `data-key` 回填表单字段（用户可编辑），并提示"请逐项人工核对"

### 5.2 请求参数

| 项 | 值 |
|---|---|
| 端点 | `https://open.bigmodel.cn/api/paas/v4/chat/completions` |
| 模型 | `glm-4v-flash` |
| 鉴权 | `Authorization: Bearer <用户自己配置的 Key>` |
| 温度 | `temperature: 0.1`（抽取任务要稳定，不要发挥） |
| 消息结构 | `messages[0].content` = `[{type:"text",text:<提示词>}, {type:"image_url",image_url:{url:<dataURL>}}]` |

### 5.3 容错与降级

| 失败情形 | 处理 |
|---|---|
| 未配置密钥 | 上传即提示"已自动切换手录"，主流程零阻塞 |
| 图片读取失败 | 提示"图片读取失败，请重试或改手录" |
| HTTP 非 2xx | 读取服务端 error.message 并展示，保持手录可用 |
| 返回非 JSON / 含代码围栏 | `parseOcrJson` 剥离 ```json 围栏后重试解析 |
| 解析出空对象 | 提示"未返回可回填字段，请检查图片清晰度或改手录" |

**原则**：OCR 是"省打字"的增强项，不是关键路径；任何失败都不阻塞体检流程。

### 5.4 密钥与隐私

- 密钥仅存 `localStorage`，不上传第三方（识别请求直连智谱）
- 未配置密钥 = 完全离线可用，评审可直接双击运行
- 隐私页提供"清除本地全部数据"，一键清空草稿/档案/误报/密钥

## 六、提示词工程策略

### 6.1 当前提示词（P1，OCR 字段抽取；提示词版本与规则库版本独立）

```text
你是食品包装信息抽取助手。识别这张食品包装/标签图片，提取下列字段并严格返回一个 JSON 对象（不要 markdown 代码块、不要多余文字），识别不出的字段省略：
productName 产品名称；category 申报品类；producer 生产者/生产企业；origin 产地/生产地址；spec 净含量/规格；produceDate 生产日期（格式 YYYY-MM-DD）；shelfLife 保质期；scNumber 食品生产许可证编号（SC 开头）；uscc 统一社会信用代码（18 位）。
只返回 JSON 对象本身。
```

### 6.2 设计要点

| 设计 | 目的 |
|---|---|
| 先给**角色**（"食品包装信息抽取助手"） | 把模型约束在抽取任务，抑制解释性输出 |
| **字段白名单**（9 个 key 一一对应表单 `data-key`） | 模型输出的 key 可直接映射到表单，无需二次翻译 |
| **格式硬约束**（纯 JSON、禁 markdown 围栏、只返回对象） | 降低解析失败率；`parseOcrJson` 仍做兜底 |
| **缺失省略**（识别不出就省略） | 避免模型编造"看起来像"的值 |
| **日期格式指定**（`YYYY-MM-DD`） | 与 `input[type=date]` 及日期校验器对齐 |
| **温度 0.1** | 抽取任务求稳定、可复现，不要创造性 |

### 6.3 已知失败模式与对策

| 失败模式 | 现状对策 | 后续优化方向 |
|---|---|---|
| 返回 ```json 围栏 | 正则剥离后重解析 | 保持 |
| 字段名漂移（如 `product_name`） | 按 `data-key` 精确匹配，未匹配则忽略 | 增加 key 别名映射表 |
| 包装反光/遮挡导致漏字 | 空值不回填，提示人工核对 | 增加"重拍建议"提示 |
| 覆盖已填字段 | 界面明确提示"请逐项人工核对" | 改为"仅填充空字段"开关 |

## 七、本土场景转功能模块

工具不是先有功能再找场景，而是从山东助农直播的具体痛点倒推模块：

| 场景痛点（助农直播基地） | 观察 | 转化为功能 | 对应规则 |
|---|---|---|---|

## 八、人机协作流程

### 8.1 开发期：谁做了什么

| 环节 | 人 | AI |
|---|---|---|
| 选题与场景 | 确定助农直播选品场景、目标用户、竞品差异 | 竞品检索与差异化分析 |
| 规则整理 | 确定红线（不生成法条、条款待核对）、审定规则分类 | 起草 20 条规则结构（第三轮整改新增 R-NC-003，现为 21 条） |
| 编码 | 验收每阶段功能、提出修改 | 全部前端代码、校验算法、判定引擎 |
| 案例 | 授权案例口径（主体匿名） | 设计四态案例、执行、截图、写案例文档 |
| 测试 | 抽验结果合理性 | 48 条自测脚本、联调回归、缺陷定位与修复 |
| 文档 | 审阅 | 技术说明、AI 应用说明、使用说明初稿 |

**证据留痕**：全过程记录在 `docs/开发日志_AI协作证据.md`，按 D1–D15 逐日记录"需求输入 → AI 生成 → 人工审阅 → 修正"，含 5 处真实缺陷的发现与修复（空值误判、绿转灰、档案错配、技术键泄露、报告括号误判）。

### 8.2 产品内：人机协作被做进流程

判定结果出来后，流程上强制经过人工环节，机器不替人下结论：

1. 规则引擎给出判定条目与依据（红/黄/灰/绿）
2. 审核人对每条判定逐条裁决：**确认违规 / 标记误报 / 忽略**
3. 选择审核结论（通过 / 整改后上播 / 禁播），填写审核人与日期
4. 点击"签字生效"后写入本地档案；标"误报"的条目同时沉淀到误报库
5. 后续可据此修订规则库，形成"使用—反馈—修订"的闭环

这条设计让工具的角色明确为**辅助决策**：机器负责"查得到、查得一致"，人负责"担责任"。

### 8.3 自律红线（对外统一口径）

1. AI 不生成法条；条款号未核对完的标【待核对】
2. 不做联网验真：USCC 只算校验位、SC 只校结构
3. 报告比对 ≠ 真伪鉴定：只识别"报告与申报品不匹配"
4. 四态不误杀：信息不足判灰，食用农产品不要求 SC
5. 人工签字生效：判定是提示，结论须签字
6. 案例为演示数据：主体匿名、证号为虚构值

## 十、业务价值

1. **把"合规"从人脑经验变成可复核流程**：同样一份资料，谁查、哪天查，结论一致；每条结论都能点开看依据。
2. **降低误杀带来的生意损失**：初级农产品不必因"没有 SC"被挡在门外；信息不全的品走"补资料"而不是"判违规"。
3. **缩短选品沟通成本**：黄态直接出整改单，写明改哪、怎么改、依据什么、几天内完成，减少来回扯皮。
4. **留下可追溯的责任链**：谁裁决、谁签字、哪天签的，都在本地档案里；出问题能复盘。
5. **适配基层现实条件**：零部署、离线可用、不传资料，适合网络与 IT 条件有限的助农直播基地。
6. **可扩展**：规则库与引擎分离，新增品类/平台只需改 JSON；误报沉淀机制让规则能随使用迭代。

> 政策与法规依据以人工编审后的规则库为准，条款号未核对项一律标【待核对】，不在文档中虚构法条。
>
> 2026-10-25 已核对并写入规则库的对口依据包括：《广告法》第九条第（三）项、第十七条、第十八条；《食品安全法》第三十四条第（八）（十）项、第三十五条、第七十三条第一款、第七十八条；GB 7718-2011 第 4.1.1 条；GB 28050-2011 第 7 章；以及 **2026-03-20 施行的《直播电商经营者落实食品安全主体责任监督管理规定》（市场监管总局令第 120 号）第十六条、第十八条、第十九条**（用于 R-COM-001/002/004/006、R-YB-001/006、R-NC-003）。
